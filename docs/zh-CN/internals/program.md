# GBC 程序

`kohakugbc/program/gbc.kir` 表示一张图像的完整处理任务：输入为图像、已有描述及标签和控制项，输出为 GBC 图（JSON 文本）及统计计数。`kohakugbc.nodes.library.build()` 构建其 `gbc` 节点库。所有值都通过参数传入和返回，节点不会修改输入。

## 结构

| `@def` | 作用 |
|---|---|
| `ask` | 发出 VLM 请求；失败时按 GBC 的处理方式返回空回复 |
| `detect` | 在父节点边界框内检测已命名实体的区域，向下一层展开 |
| `root` | 图像顶点：GBC 图像查询，或现有描述（纯文本、图文、标签） |
| `expand` | 处理单个区域：通过 `register` 合并到已见过的同一对象，或描述它并检测组成部分 |
| `prefill` | 在一次请求中处理多个区域（`entity_batch` 大于 1） |
| `wave`、`depth_round` | 一轮处理：以轮次开始时的待处理队列为边界，分批处理节点预算允许的区域 |
| `coverage` | 生成一条新的根描述句，找出此前未覆盖的对象 |
| `relate` | 针对当前图提出关系和组合问题 |
| `gbc` | 主任务：根节点、轮次直到 `next_step` 结束、关系问题、图的生成 |

模型节点只负责传输：`chat`（请求输入、回复文本输出）、`detector`（图像块及请求输入、原始框输出）、`embedder`（名称输入、向量输出）。请求构造器（`kohakugbc.nodes.specs.chat`、`detect`）和回复解析器（`parse`）都是普通节点，因此任意引擎都会执行相同的请求构造及解析逻辑。

## 复现 PoC

节点移植了 PoC 的轮次执行器（`gbcpoc.engine.runner`）、JSON 回复层、种子根节点，以及 ml-gbc 的解析器、检测后处理、同对象合并和关系查询。六组 PoC 运行被记录为轨迹（`scripts/trace/poc_arms.py`：纯文本、图文、标签和图像查询的根节点；实体批大小 4；使用父回复生成叶节点描述；每组 30 张图像），并通过 KIR 参考解释器运行程序回放（`scripts/trace/replay_program.py`）。

程序与 PoC 的差异及原因：

| 差异 | PoC | 当前程序 |
|---|---|---|
| 提示词文本 | 按系统区域设置编码读取（录制机器为 cp950），使图像查询系统提示词中的非 ASCII 字符乱码 | 全部按 UTF-8 读取 |
| 未设种子的随机选择 | 关系数量、子节点集合的命名短语、组合根与措辞取自未固定种子的生成器 | 根据提问内容为生成器设定种子（`draw.rng`）；录制运行使用同样的随机结果 |
| 关系句子 | 通过 `set` 去重，顺序由进程哈希种子决定 | 按首次出现顺序去重；录制运行也使用相同规则 |
| `relational = "relation"` / `"composition"` | 两者各自仍包含另一类问题 | 两者分别只保留自己的问题类型 |
| 名称嵌入 | 只有同对象比较需要时才对名称编码 | 对所有区域的名称进行编码（在嵌入通道批处理）；判断结果一致 |
| 关系问题 | 每轮后发问，并根据输入缓存回答 | 默认只在结束时询问一次（`relate = "end"`），最终图提出相同的问题；`"every_round"` 在每轮后输出图 |
| 区域注册 | 查询后在图像级锁保护下注册 | 查询前按程序顺序注册；与 PoC 每轮逐个区域处理的顺序一致 |

因此，每个回放任务产生的图按摘要与 PoC 完全一致，而且程序发出的每次请求都曾由 PoC 发出。`tests/program` 使用各组截取的任务（`tests/fixtures/traces`）验证这些性质，也检验破坏待处理队列顺序会改变图。
